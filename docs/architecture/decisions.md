# Архитектурные решения

Короткие записи о ключевых решениях: что решили, почему и что отвергли. Новые решения добавляются в конец, старые не переписываются — если решение меняется, появляется новая запись со ссылкой на прежнюю.

---

## 1. C# вместо PowerShell

**Контекст.** Первая версия была PowerShell-скриптом на 35 строк (`git-automerge-loop.ps1`). Для мини-теста этого хватало, но для инструмента нужны разбор и проверка JSON, статусы результата, обработка ошибок и тесты.

**Решение.** Переписать на C# под .NET 10 (LTS): консольное приложение и xUnit-тесты.

**Почему.**
- Все-таки PowerShell - это было для интереса, а на C# понятнее и глубже покопаться мне лично было интересно.
- Типизированная модель задачи и `System.Text.Json` вместо ручного разбора.
- Тесты, которые запускают настоящий `git` на временных репозиториях, — 130+ сценариев, включая отказ хуков и падение push.
- .NET кроссплатформенный: тот же код работает на Windows у разработчика и на Linux в GitHub Actions.

**Отвергнуто.**
- *Оставить PowerShell* — тестировать и сопровождать логику со статусами и откатами - я бы не вывез.
- *Python* — рассматривался как самый простой вариант для JSON и CI, но C# победил.

## 2. Каждая ветка от `main`, а не цепочка веток

**Контекст.** В стресс-тесте каждая ветка создавалась от предыдущей. Это убрало конфликты, но только потому, что сценарий был вырожденным: один файл, только дописывание. Каждый PR содержал все предыдущие коммиты.

**Решение.** Каждая задача — независимая ветка от свежего `base`, полученного из `origin`.

**Почему.**
- В цепочке первый же красный CI блокирует все следующие PR: они содержат тот же коммит.
- PR должен содержать ровно одно изменение, чтобы его можно было проверить и откатить отдельно.
- Ветка от свежего `origin/main`, а не от локального `main`, не зависит от того, насколько давно обновлялась рабочая копия.

**Отвергнуто.** *Цепочка веток* — хороша для нагрузочного теста, непригодна для реальных независимых задач.

## 3. Временный `git worktree`

**Контекст.** Движок должен создавать ветки и коммиты в репозитории, где человек может параллельно работать: открыт редактор, есть незакоммиченные правки.

**Решение.** Все изменения делаются во временной папке через `git worktree add`, которая удаляется после работы. Ветка с коммитом остается в репозитории.

**Почему.**
- Текущая ветка и незакоммиченные файлы разработчика не трогаются.
- Не нужно требовать «чистую» рабочую копию перед запуском.
- Если процесс прервется, в рабочей копии не останется наполовину примененных изменений.

**Отвергнуто.** *Работа прямо в рабочей копии* — проще и нагляднее, но движок переключал бы ветки под руками у человека.

## 4. Никакого `push --force`; при неудаче убирать за собой

**Контекст.** Старый скрипт делал `git branch -D` и `git push -f`. Для теста это удобно, но так можно молча уничтожить чужую работу.

**Решение.**
- Push только без `--force`.
- Если ветка уже существует локально или в `origin`, движок останавливается со статусом `BranchExists` / `RemoteBranchExists` и ничего не трогает.
- Если доставка не удалась на любом шаге, движок удаляет то, что создал в этом запуске, — и только это.

**Почему.** Повторный запуск должен быть безопасным: либо задача уже доставлена и об этом сообщается, либо после неудачи все начинается с чистого листа.

## 5. GitHub CLI (`gh`) вместо Octokit или прямого API

**Решение.** PR, метки, auto-merge и состояние PR — через вызов `gh` как процесса, за интерфейсом `IGitHubClient`.

**Почему.**
- Авторизация берется из уже выполненного `gh auth login`: движку не нужно хранить токены.
- Меньше зависимостей; тот же инструмент, что и в исходном скрипте.
- Интерфейс позволяет тестировать всю логику с подделкой (`FakeGitHubClient`) без сети и без GitHub.

**Отвергнуто.** *Octokit / REST API* — может понадобиться позже (например, для GitHub Action без `gh`). Интерфейс оставляет эту замену дешевой.

## 6. Метки — предупреждение, auto-merge — отдельный статус

**Контекст.** После создания PR могут не сработать два шага: добавление меток (метки нет в репозитории) и включение auto-merge (выключен в настройках репозитория).

**Решение.**
- Неудача с метками — только предупреждение, доставка считается успешной.
- Неудача с auto-merge — статус `AutoMergeFailed`, код выхода 3, но PR остается открытым.
- Если не удалось создать сам PR, запушенная ветка удаляется (`PullRequestFailed`).

**Почему.** Метка — косметика, ее можно добавить руками. Auto-merge — часть обещания «изменение само дойдет до `main`»: если он не включился, вызывающий скрипт или агент должен об этом узнать. Удалять при этом уже созданный PR незачем — его можно смержить вручную.

## 7. Ожидание результата опросом, с таймаутом

**Решение.** С флагом `--wait` движок раз в 15 секунд запрашивает состояние PR, максимум 30 минут. Итог: `Merged`, `CiFailed`, `PullRequestClosed` или `WaitTimedOut`. Во всех случаях, кроме слияния, PR остается как есть.

**Почему.** Опрос через `gh pr view` прост и не требует входящих соединений. Для одиночных задач и пакетов в десятки PR нагрузка на API незначительна.

**Отвергнуто.** *Webhooks* — требуют доступного извне сервера; избыточно для консольной утилиты.
